# Leafline ポートフォリオ説明

面接などで説明するための資料です。何を作ったかは [README](../README.md)、細かい仕様は各定義書にあります。ここでは「**なぜそうしたか**」「**どこで苦労し、どう解決したか**」をまとめます。

---

## 1. 作った目的

- **Web アプリを、要件定義から公開・運用の準備まで、ひと通り 1 人でやり切る**こと。画面を作るだけでなく、設計書・テスト・公開・ログ・負荷の確認までを経験したかった
- 題材に SNS を選んだ理由: ログイン、投稿と画像、人と人のつながり(フォロー・ブロック)、リアルタイムの配信、検索、管理者の機能と、Web アプリでよく出てくる要素が一通り入っているため
- 前に作ったタスク管理アプリ(taskboard)で覚えた Spring Boot・React・Docker を土台に、今回は「**長く運用できる作り**」を目標にした

## 2. 技術を選んだ理由

| 決めたこと | 選んだもの | 理由 | 比べたもの |
|---|---|---|---|
| サーバー | Java 21 + Spring Boot 4 | 型があり、大きくなっても直しやすい。ログイン・権限・CSRF は Spring Security の仕組みに乗せ、自分で作らない | Node.js(Express) |
| ログイン状態 | サーバーのセッション(Cookie。データベースに保存) | **利用停止・ログアウトをすぐに反映できる**(リクエストのたびに状態を確かめている)。Cookie を `HttpOnly` にでき、画面のプログラムから読まれない | JWT(発行したあとに取り消しにくい) |
| リアルタイム | Server-Sent Events | 必要なのはサーバー → ブラウザの一方向だけ。ふつうの HTTP のままなので、Caddy・Spring MVC・ログイン状態がそのまま使え、切れてもブラウザが自動でつなぎ直す | WebSocket(双方向で、この用途には大きい) |
| 一覧の続き | カーソル方式(「この ID より古いもの」) | 読んでいる間に新しい投稿が増えても、**同じ投稿が二重に出たり、飛ばされたりしない** | ページ番号(OFFSET) |
| データベース | PostgreSQL | ユーザー・投稿・フォローなど、つながりの多いデータに向く。テストでも同じ PostgreSQL を使う | MySQL |
| テストの DB | Testcontainers(本物の PostgreSQL) | 本番と同じ DB で試すので、SQL の書き方の違いで本番だけ壊れることがない | H2(メモリの DB) |
| テーブルの変更 | Flyway | 変更が番号付きの SQL として残り、本番にも同じ順で流れる。起動のときにコードとテーブルの食い違いを見つける | Hibernate の自動作成 |
| 画面 | React + Vite、CSS はライブラリなし | 部品に分けて作れる。CSS を自分で書き、見やすさ(色の差・キーボード操作)を細かく決めた | UI ライブラリ |
| 公開 | AWS EC2(t4g.micro)+ Docker Compose + Caddy | 1 台で安く動かせる。Caddy が HTTPS の証明書を自動で取り、更新する。**使うときだけ起動**して、費用を抑える | ECS・RDS(月の費用が数倍) |
| サーバーの操作 | Systems Manager(SSH は使わない) | 22 番のポートを開けずに済む。サーバーには IAM ロールで最小限の権限だけを渡し、アクセスキーを作らない | SSH |

## 3. 設計で工夫したこと

### 性能: N+1 を防ぎ、テストで守る
投稿の一覧を返すとき、画像・いいねの数・いいね済みか・返信の数などを、**何件あってもそれぞれ 1 回の SQL でまとめて取る**ようにした([PostViews.java](../src/main/java/com/example/sns/post/PostViews.java))。
さらに、テストで実際の SQL の回数を数え、投稿が 1 件でも 20 件でも回数が変わらないことを確かめている。あとから誰かが直して N+1 に戻っても、テストが失敗して気づける。

### 「誰に何が見えるか」を 1 か所で決める
ブロック(お互いに見えない)、ミュート(自分の画面からだけ消える)、管理者の非表示、利用停止中の人の投稿。この見え方のルールは、タイムライン・検索・通知・リアルタイム配信のどこでも同じでなければならない。ルールを 1 か所([Relations.java](../src/main/java/com/example/sns/profile/Relations.java) の `VISIBLE_TO_VIEWER`)にまとめ、タイムライン・検索・通知などの SQL が同じものを使うようにした。リアルタイム配信でも、ブロックした相手には新着を届けない。

### 新着の出し方
最初は、新着を自動で先頭に足していた。ところが、読んでいる途中に一覧が動くと読みにくい。X と同じく、**新着はためて「新しい投稿が ○ 件あります」で知らせ、押したときに表示する**形に変えた。読んでいる途中に新着が届いても、見ている投稿の位置が動かない(2px 未満)ことを、E2E で測って確かめている。

### 安全
- すべての API で、ログイン・本人・管理者かをサーバー側で確かめる。管理者の API は、管理者以外には「見つかりません」(404)を返し、あることも知られないようにした
- ログインの失敗は、メールアドレスとパスワードのどちらが違うかを教えない。**登録されていないメールアドレスでも、パスワードの照合と同じだけ時間をかける**(時間の差で、登録の有無を推測されないように)
- 画像は、拡張子ではなく**中身で形式を確かめる**。送る前にブラウザで縮小し、写真の位置情報も消える
- Content-Security-Policy で、画面が読み込めるものを自分のサイトに限る(仮に XSS があっても、外へ送れない)

### 見やすさ(アクセシビリティ)
- 文字と背景の明るさの差を、ライト・ダークとも**自動テストで計算して確かめる**(色を変えて読みにくくなれば、テストが失敗する)
- いいね済み・未読・エラーなどの状態を、色だけでなく文字や形でも示す
- キーボードだけで操作でき、ダイアログを閉じるとキーボードの位置が元に戻る

### 運用
- **ログは 1 行 1 件の JSON**。リクエストごとの番号を付け、予想外のエラーでは利用者に「エラー番号」を見せる。問い合わせの番号から、そのときのログをすべて探せる。パスワード・メールアドレス・検索の言葉はログに残さないことを、テストで確かめている
- **テーブルの変更は Flyway**。本番に最初に入れるときは、本番のテーブル定義を読み取って比べ、バックアップをとってから反映した
- **登録せずに試せるお試しログイン**。みんなで使う 1 つのアカウントで、プロフィールは変えられず、書き込みは毎日消える

## 4. テストの考え方

| 層 | 道具 | 数 | 何を守るか |
|---|---|---|---|
| 単体テスト | JUnit・Vitest | サーバー 6 クラス・画面 74 件 | 計算や文字の扱い、色の組み合わせなど、小さな決まり。1 件 数ミリ秒 |
| 結合テスト | JUnit + Testcontainers | 約 20 クラス | API を本物の DB とつないで。権限・ブロック・N+1・ログの中身など |
| 操作テスト(E2E) | Playwright + Edge | 11 本・234 項目 | 利用者の大事な流れ(登録・投稿・フォロー・新着・管理者など) |
| 見やすさの点検 | Playwright | 全画面 × 2 つの幅 × ライト・ダーク | 横スクロール・名前のない部品・フォーカスの枠 |
| 負荷テスト | k6 | 30〜60 人 | 速さ・エラー・メモリ |

- 細かい確認は速いテストで行い、E2E は大事な流れに絞った。プッシュのたびに CI(GitHub Actions)で流れ、全部で 4〜5 分
- 不具合は、**先にテストで再現してから直す**(TDD)。管理者のユーザー検索の不具合は、この手順で直した(下の 5.3)

## 5. 苦労したことと、どう解決したか

### 5.1 手元では通るのに、CI のテストだけ失敗した
Windows で作った `mvnw`(Maven を動かすファイル)に、Linux で「実行してよい」という印が付いていなかった。CI(Linux)でだけ「Permission denied」になった。git にファイルの実行権限を記録して直した。**作る環境と動かす環境の違い**を意識するようになった。

### 5.2 E2E が、たまにだけ失敗した
タブを押した直後に、まだ前のタブの一覧が表示されているうちに、中身を調べてしまっていた。手元の速い PC では起きず、CI の遅い環境でだけ起きた。「**選んだタブに切り替わったことを確かめてから、新しい一覧を待つ**」共通の関数を作り、3 か所を直した。

### 5.3 管理者のユーザー検索で、`_` を入れると全員が出た
SQL の `LIKE` では、`_` と `%` が特別な意味を持つ。ほかの検索では打ち消していたが、管理者の検索だけ漏れていた。**先にテストで失敗を再現**し、打ち消す処理を 1 つの部品(`LikePatterns`)に集めて、3 か所にあった同じ処理もそれに置き換えた。

### 5.4 負荷テストの結果が、測り方で大きく変わった
最初は、コンテナごとに CPU を細かく仕切って測り、60 人で 95% が約 2 秒と遅かった。調べると、DB が自分に割り当てた CPU の上限に張り付いていた。本番のサーバーでは、アプリと DB が 2 つの CPU を分け合うので、**測り方を本番に近づけ直した**(同じ 2 コアを分け合う)。結果は 60 人でも 95% が 30ms 前後になった。両方の結果を残し、手元の CPU は本番より速いので楽観的であることも書いた。

### 5.5 ログを作ったら、別の不具合が見つかった
構造化ログの確認で、メールの送信に失敗させてみたところ、**登録が取り消されたのに「登録しました」のログだけが残る**ことに気づいた。ログを出す位置が、メールを送る前だったため。送れたあとに出すように直し、テストも足した。

### 5.6 テストデータの仕組みが、開発用のアカウントを消していた
テストデータを入れ直す仕組みが、データベースの**すべてのユーザー**を消していた。開発中に Google で作ったアカウントが、そのたびに消えていた。消すのはテストデータのユーザーだけにし、「入れ直しても、ほかのアカウントは残る」テストを足した。

### 5.7 AWS への公開
サーバーの初期設定のスクリプトに日本語のコメントを入れたところ、文字コードの扱いで AWS に渡せなかった。また、Docker のイメージを作る部品が足りなかった。1 つずつ原因を調べて直し、**起動・停止・更新を PowerShell のコマンド 1 つ**でできるようにした(`start.ps1`・`stop.ps1`・`start.ps1 -Update`)。

## 7. 今後の改善

- **エラーの通知**: 今はログを調べられるが、エラーが出ても誰も気づけない。CloudWatch に送り、エラーが出たらメールで知らせる
- **バックアップから戻す練習**: 毎日バックアップをとっているが、戻す手順を定期的に試す
- **Java 25(次の長期サポート版)への更新**
- **検索の速さ**: 今は `LIKE` での検索。投稿が増えたら、全文検索の仕組み(PostgreSQL の拡張など)に切り替える
- **機能**: リポスト(他の人の投稿の共有)、ダイレクトメッセージ
